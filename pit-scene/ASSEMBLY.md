# Theme 1 pit kit: assembly guide for the Unity implementer

Everything in this guide is generated by scripts in `tools/`, so it can be rebuilt:
```
python3 tools/make_atlas.py                         # textures/T1_Scenery_Atlas.png
/opt/homebrew/bin/blender -b -P tools/build_kit.py  # kit/fbx, kit/glb, kit/t1_kit.blend, kit/kit_report.json
/opt/homebrew/bin/blender -b kit/t1_kit.blend -P tools/assemble.py -- --cols 7 --rows 9 --balls --out preview/t1_board_7x9.png
```
`tools/assemble.py` is the reference implementation of the layout rules below. If anything here is unclear, read `layout_board()`.

Lighting, fog and camera values are in [LIGHTING.md](LIGHTING.md).

**Camera:** style.md §2 (2026-10-19) uses a 30° downward view from behind the player. At that angle the kit shows:
- the wall tops: the coping, the pillar caps and the chipped block on BrickB all have top faces;
- the trench narrowing into the fog at the far end.

Wall back faces (the side facing out of the pit) are left out. They always face away from a camera inside the pit; don't move the camera outside the walls.

## 2. Grid
- **1 slot = 1 cell = 1.125 units** (spec §0). Every wall segment is exactly one cell long, so a wall run of any length snaps to the board's row grid.
- The board is centred on the `PitRoot` origin.
  - Columns run along local X. Rows run along local Z: the far end, where enemies come from, is +Z.
  - Local Y is up, out of the floor, toward the camera.
- Row-cell centres sit at z = k × 1.125 for integer k: odd row counts (9, 11, 13, 15) are centred on k = 0.
- The wall collision line (the ball-bounce edge) is at x = ±cols/2 × 1.125:

| Board | Wall face x |
|---|---|
| 7×9 | ±3.9375 |
| 9×11 | ±5.0625 |
| 11×13 | ±6.1875 |
| 13×15 | ±7.3125 |

### PitRoot in the game's frame
The game board is in world XY and the camera looks along +Z. Make an empty `PitRoot` with:
- position = board centre at the play plane;
- rotation = **(−90, 0, 0)**.

Its local +Y then points at the camera (world −Z), and its local +Z points screen-up (world +Y). All the numbers below are PitRoot-local.

## 3. Pivots and orientation (every piece)
- **The origin is at floor level, at the centre of the piece along the wall, on the collision face.**
- **The prefab's forward (+Z) points into the board.** The brick face is the side the player sees. The wall body extends behind, to −Z (outside the board).
- Wall pieces span local x ∈ [−0.5625, +0.5625] and stand 4.7 tall (the pillar is 5.15).
- Below a height of 1.5, nothing sticks out in front of the collision face (z > 0), so balls and units at the board edge never overlap the wall.
  - Above 1.5 only the coping (0.12) and the loose bricks (0.05) project. In perspective, those project outward on screen anyway.
- Floor tiles: origin at the cell centre, face up (+Y).
- Props:
  - Hook: origin at the hanging point (the top of the chain).
  - Bell shard: origin at the centre of its bottom edge.
  - Ladle: origin at the bottom of the bowl.
- Import check: in the prefab, `T1_Wall_BrickA` should be 1.125 wide and its bricks should face +Z. If the bricks face −Z, the exporter axis is off: rotate the model child 180° on Y and report it. Both the FBX and the GLB were exported for this convention. The GLB was verified: the coping overhang is at glTF +Z = +0.12.

## 4. Laying out a board (per side)
```
K_NEAR = -16, K_FAR = 21                 # slots along Z, the same for every board size
PATTERN = [Pillar, BrickA, IronRib, BrickB, Chain, BrickA, Trough, BrickB]
left  wall: x = -cols/2*1.125, rotY = +90, slot k uses PATTERN[k mod 8]
right wall: x = +cols/2*1.125, rotY = -90, slot k uses PATTERN[(k+4) mod 8], with Chain swapped for Mould
slot k = K_NEAR is always a Pillar (it closes the near end)
position of slot k: (x, 0, k*1.125)
```
- Use `((k % 8) + 8) % 8` in C#, because `%` can be negative.
- The pattern depends only on the absolute slot k. It never changes when the board grows, and both walls keep their look as they slide out.
- Floor: for i in 0..cols−1 and k in K_NEAR..K_FAR, place a tile at ((i − (cols−1)/2) × 1.125, 0, k × 1.125). It is `T1_Floor_B` when `(i*7 + k*13) % 6 == 0`, otherwise `T1_Floor_A`.
- Props (optional; positions are in the wall piece's prefab-local frame, so make them children of that wall):
  - Hook on `T1_Wall_IronRib` slots where `floor(k/8)` is even: local (0, 3.86, +0.2), no rotation. It hangs off the tie band.
  - Ladle on left-wall `T1_Wall_Trough` slots: local (−0.3, 0.45, −0.28), rotY 200, tilted 12°, leaning in the trough.
  - Bell shards lie on the floor only outside the largest board's rows (|k| ≥ 8): for example left (k 12), right (k 16), right (k −10), about 0.7 inside the wall face.
- Cost at 13×15 (everything placed): about 25k verts in about 1 draw call per batch (one material). Mark everything Static (static batching), or combine each wall run into one mesh at load. You can also cull slots with k > rows/2 + 12; they are fully fogged.

## 5. Board expansion (7×9 → 9×11 → 11×13 → 13×15)
Each Boss expansion adds one column on each side and one row at each end (spec §1.3). The 3-second animation runs alongside the camera pull-back. For each expansion:
1. **Walls:** tween the left run's x from −cols_old/2 × 1.125 to −cols_new/2 × 1.125 (exactly −1.125), and the right run by +1.125. Each side is one parent object, so it is one tween. Ease to match the camera; use the screen shake from the spec.
2. **Floor:** at the start of the tween, spawn one new floor column per side at x = ±(cols_new − 1)/2 × 1.125 for every k. It starts hidden under the wall body (the body is 0.97 deep), and the sliding wall uncovers it.
3. **Rows:** nothing to do. The run already covers k −16…21, which holds the 15-row board plus the near margin and the fogged far trench.
   - If the game grows the board only toward one end instead of symmetrically, move `PitRoot` by half a cell per added row in the opposite direction instead. The slot pattern stays valid because it is keyed by absolute k.
4. **Camera, fog and spot:** recompute and tween them as LIGHTING.md says.

Collision walls stay in game code (2D), at the same x values as the wall faces.

## 6. Material and atlas
- **One material for every piece: `T1_Scenery`.**
  - Shader: URP/Lit (or Simple Lit). Base Map = `textures/T1_Scenery_Atlas.png`, colour white.
  - Metallic 0, Smoothness 0.1, no normal map, no emission. GPU Instancing on.
- Import settings for each FBX/GLB:
  - Scale factor 1 (FBX: Convert Units on; one Unity unit = 1 m = the Blender unit).
  - Materials: **None** (FBX Material Creation Mode = None), or remap the embedded material to `T1_Scenery`.
  - Normals: Import. Read/Write off. Mesh compression Medium.
- Atlas import:

| Setting | Value |
|---|---|
| Texture type | Default, sRGB on, no alpha |
| Max size | 1024 |
| Wrap | Clamp |
| Filter | Bilinear |
| Mipmaps | On |
| Compression | ASTC 6×6 (WebGL / TikTok) or ETC2 fallback |
| Size | about 64 KB as PNG, about 0.2 MB compressed with mips |

  Brick UVs touch the atlas edges, so the far mips can bleed a little. That is invisible at the fog distance.
- Atlas layout (pixels, top-left origin; defined in `tools/make_atlas.py` and `tools/build_kit.py`):

| Region | Pixels | Content |
|---|---|---|
| brick A | 0–255 × 0–1023 | one segment face (1.125 × 4.5), tiles left/right |
| brick B | 256–511 × 0–1023 | the same, damaged |
| stone | 512–767 × 0–511 | dressed blocks |
| floor A / B | 512–767 × 512–767 / 768–1023 | one cell each |
| iron / clay / bronze | 768–1023, 256 px bands | material tiles |
| swatches | 768–1023 × 768–831 | 16 flat 32 px colours |

- Values: atlas V p5/p50/p95 = 8 / 18 / 29 %, S p50/p95 = 30 / 44 %, inside style.md §4's scenery range. The hue is slate-teal H195 from the art bible. The props' bronze, clay and copper sit at the top of the range.
